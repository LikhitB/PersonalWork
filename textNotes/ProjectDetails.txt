Session 101: activeViolation = TRUE (in Redis)

Frame A (no violation) → Virtual Thread 1 (VT1) starts
Frame B (no violation) → Virtual Thread 2 (VT2) starts

VT1: requiresClearanceNotification(101) → reads Redis → TRUE ✅ "I should clear"
VT2: requiresClearanceNotification(101) → reads Redis → TRUE ✅ "I should clear"
     ↑ VT2 reads SAME TRUE because VT1 hasn't cleared yet!

VT1: publishInferenceResult(...)   ← takes ~200ms network time
VT2: publishInferenceResult(...)   ← ALSO runs, duplicate publish!

VT1: markViolationsCleared(101) → Redis = FALSE
VT2: markViolationsCleared(101) → Redis = FALSE

RESULT:
✅ State is cleared
❌ TWO clearance messages sent to Ably/Service Bus

Session 101: activeViolation = TRUE (in Redis)
----------------------------------------------------------------------
Frame A (no violation) → Virtual Thread 1 (VT1) starts
Frame B (no violation) → Virtual Thread 2 (VT2) starts

VT1: checkAndClearIfActive(101)
       → reads Redis  → TRUE
       → writes FALSE → immediately
       → returns TRUE ✅ "I should publish"

VT2: checkAndClearIfActive(101)
       → reads Redis  → FALSE (VT1 already cleared it!)
       → returns FALSE ❌ "Nothing to do"

VT1: publishInferenceResult(...)   ← only VT1 publishes
VT2: does nothing, moves on

RESULT:
✅ State is cleared
✅ Only ONE clearance message sent

-----------------------|---------------------------------|------------|------------------|------------|----------

JOB CONFIG FIELDS EXPLAINED

Field            | Meaning
-----------------|-----------------------------------------------------------
queueName        | Actual Azure Service Bus queue name
maxRetries       | App-level retries (opcommons handles). 0 = no retry
progressiveRetry | If true, delay doubles between retries (exponential backoff)
startDelay       | Initial delay before first execution attempt
retryDelay       | Wait time between retries (irrelevant when maxRetries=0)


RETRY LAYERS (Two Independent Levels)

Layer              | Config Field      | Current Value | What Happens On Failure
-------------------|-------------------|---------------|-------------------------------------------
App-level          | maxRetries        | 0             | Job fails once, no retry at app layer
Broker-level       | maxDeliveryCount  | 1             | Message delivered once, if not completed -> DLQ


MESSAGE LIFECYCLE (With Current Settings)

Step | What Happens
-----|----------------------------------------------------------------------
1    | Message pushed to queue (may have scheduled delay)
2    | After delay expires, message becomes VISIBLE
3    | Listener picks it up, message LOCKED for 5 min (lockDuration)
4    | If processing takes longer, SDK auto-renews lock up to 15 min
5a   | SUCCESS: message completed, removed from queue
5b   | FAILURE: message abandoned, redelivered
6    | After 1 failed delivery (maxDeliveryCount=1), message goes to DLQ
7    | If never consumed within 24h (TTL), message is DROPPED (not DLQ)

4.RETRY & ERROR HANDLING DESIGN
--------------------------------
LAYER 1: PUSH RETRY (sending message to Azure)
  WHO:    ServiceBusWrapper.pushScheduledMessage()
  WHAT:   If Azure rejects/timeout on send, retry up to 3 times
  HOW:    for-loop with closeSender + fresh connection each attempt
  SCOPE:  Only retries the SEND operation, not job execution

LAYER 2: APP-LEVEL RETRY (job execution failure)
  WHO:    ServiceBusWrapper.receiveMessage() catch block
  WHAT:   If doWork() throws, re-push job as new scheduled message
  HOW:    Increment retries counter, calculate delay, pushScheduledJob()
  SCOPE:  Self-scheduling retry (new message per attempt)
  CONFIG: maxRetries=0 (DISABLED), progressiveRetry=false

LAYER 3: BROKER-LEVEL RETRY (Azure redelivery)
  WHO:    Azure Service Bus infrastructure
  WHAT:   If message not completed (lock expires/abandon), redeliver
  HOW:    Azure tracks deliveryCount, compares to maxDeliveryCount
  SCOPE:  Same message redelivered (not a new message)
  CONFIG: maxDeliveryCount=1 (ONE attempt only, then DLQ)

GEMINI INFERENCE QUEUE DETAILS
================================

Image upload
   ↓
Gemini inference
   ↓
GeminiInferenceResultProcessingService
   ├─ violation found → push to Gemini inference queue
   │    - carries job timestamp
   │    - also carries scan/gemini timestamp if present
   └─ no violation     → if previous bad state, still push for clearance; else ignore/delete blob
                        - clearance path keeps job timestamp
                        - OCR may later replace it with image timestamp
            ↓
GeminiInferenceResultHandlerJob (queue consumer)
   ├─ violation → Ably "NOTOK" / violation event
   │    - prefers `scanTimestamp` from Gemini
   │    - falls back to job timestamp
   │    - DB save uses scan timestamp if present, else job timestamp
   └─ no violation → Ably "OK" / `noActiveEvents` clearance event
        - uses OCR timestamp if readable
        - otherwise falls back to job timestamp
